In plain English

Emails now look like emails. The two visible additions:

  • Embedded images show up. Company logos and signature graphics that used to appear as broken-image icons now render properly.
  • Attachments are listed. Real attachments (a PDF, a spreadsheet, a note.txt) appear as a tidy list at the top of the email, with their type and size.

And it all still happens with zero internet access — the images are pulled out of the email file itself, not downloaded from anywhere.

How embedded images work (the "cid:" trick)

When a company puts a logo in an email, the image isn't typed into the HTML — it's shipped as a separate part of the email file and the HTML just points to it with a label, like <img src="cid:logo@acme">. "CID" means Content-ID — an internal reference, not a web address.

A normal browser has no idea what cid:logo@acme means, so it shows a broken image. Our fix: during import we find each embedded part, convert its raw bytes into a self-contained data: URL (the image encoded directly as text), and swap every cid: reference for that. The result is a body that carries its own images inside it — nothing to fetch, so nothing can leak out.

Order matters: resolve, then sanitize

We resolve the cid: images first, then run the safety sanitizer. That ordering is deliberate: the sanitizer is configured to keep data: images, so the resolved logos survive the cleaning pass. We handle images referenced three ways — in <img> tags, in inline style="background:url(...)", and inside <style> blocks.

Inline images vs. attachments

One subtlety: a logo is technically an "attachment" too, but you don't want your signature graphic cluttering the attachment list. So we tag each part: if it's referenced inline in the body (has a Content-ID or is marked "inline"), it shows in the body only. Everything else (the real PDF, the spreadsheet) shows in the attachment list. The test email demonstrates both at once — an inline logo and a separate note.txt.
